# 知识库 / 收藏夹 / 搜索 调研与重构方案

> 日期：2026-07-23（2026-07-25 复审修订）
> 状态：调研方案（产品方向已确认，待拆分执行计划）
> 范围：智能检索、内容库管理、收藏夹、内容副本与笔记正文版本
> 后续执行：见 `knowledge-favorites-search-master-execution-plan-2026-07-25.md`

## 0. 结论先行

现有“知识库”“搜索”“收藏夹”和“资料库”均已有可用基础，本轮不是从零开发，而是统一用户入口、修正数据身份、补齐精确检索和内容组织能力。

已确认的产品方向：

1. **一个“智能检索”页面**：默认同时展示 AI 综合回答和可核验、可跳转的原文来源，不再设计“智能回答 / 原文结果”两个重复标签页。
2. **另设“精确查找”模式**：只做关键词匹配和原文列表，不生成 AI 回答；它是检索方式，不是另一个结果页面。
3. **来源形成闭环**：回答中的引用编号定位对应来源卡片；来源可展开上下文、跳到笔记/转写/媒体时间点并一键收藏。
4. **内容复制后独立修改**：素材加入另一个合集时生成独立副本；不同副本不互相覆盖，但保留同源关系，可查看同源副本在其他合集中的修改版本。
5. **版本控制先覆盖用户手工编辑的笔记正文**；现有 AI 总结版本机制继续沿用，不重复建设。
6. **SQLite 分阶段引入**：先做可重建的 FTS5 全文索引；内容身份明确并迁移稳定后，再承载标签、文件夹、收藏分组等权威元数据。避免 JSON 和 SQLite 长期双写两套权威数据。

重构后保留三类正交职责：

| 模块 | 职责 | 一句话 |
|---|---|---|
| 智能检索 | 找东西、核验原文 | “回答我的问题，也让我看到证据” |
| 内容库管理 | 组织东西、查看同源版本 | “东西在哪、如何分类、有哪些副本和版本” |
| 收藏夹 | 快速访问 | “保存我认为重要的内容” |

## 1. 现状梳理（基于当前代码与本地数据）

### 1.1 功能现状

| 模块 | 当前实现 | 主要缺口 |
|---|---|---|
| 知识库问答 | `POST /knowledge/ask`；全局/范围缓存索引；AI 回答、引用来源、索引状态与手动刷新 | 与搜索入口和输出重复；索引生命周期只存在于知识库页面 |
| 搜索 | `POST /search`；并行检索多个合集；AI 回答、来源列表、范围和历史 | “关键词”按钮不可用；没有本地全文索引；与知识库问答重复 |
| 收藏夹 | `WorkspaceRecord.favorites` 保存 `item_id`；按媒体类型聚合展示 | 检索结果不能直接收藏；没有分组和收藏内查找 |
| 资料库 | `LibraryPage` 展示合集和素材；支持类型筛选、排序、视图切换、批量加入合集 | 标签仍是素材上的 Dict；没有文件夹层级、同源副本视图和手工正文版本历史 |

### 1.2 检索实现的准确差异

知识库问答和搜索确实复用了相同的来源构造、LLM 回答及底层向量检索能力，但不能描述成“搜索有 reranker、知识库没有”：

- `retrieve_with_sources` 本身已经执行 reranker，因此知识库问答也有精排。
- 跨合集搜索在各合集召回后，还会汇总候选并做一次跨合集二次精排。
- 两者真正的差异是索引组织、缓存/就绪状态和跨合集候选合并方式。

因此后续目标应是：

> 统一查询契约、候选生成和排序策略，评估是否保留跨合集二次精排；不能把“统一 reranker”写成从无到有的功能。

展示方式也不应决定底层引擎。默认智能检索和精确查找可以使用不同检索模式，但 AI 回答、来源卡片等 UI 只是统一查询结果的不同呈现。

### 1.3 数据与测试基线

当前工作区存储为 `data/workspaces/<workspace_id>.json`，未使用 SQLite / SQLAlchemy。`CLAUDE.md` 中的“SQLAlchemy + SQLite”属于文档漂移。

2026-07-25 本地只读统计：

- 44 个 workspace JSON；
- 61 条“合集—素材”记录，60 个唯一 `item_id`；
- 已有 1 个 `item_id` 同时存在于两个合集；
- 17 条素材已有自动标签；
- 41 个 AI 总结版本，其中 9 条素材有多个总结版本；
- 当前收藏记录为 0。

当前实现会在“加入合集”时复制素材记录，但继续沿用相同 `item_id`。这与“副本可以独立修改”的产品决定不完全一致，也是后续数据建模必须先解决的问题。

知识库、全局搜索、工作区搜索和收藏 API 已有基础后端测试；当前主要缺口是前端页面、引用编号与来源映射、旧路由兼容、检索后一键收藏等跨层闭环测试。正式合并前必须保留现有后端基线并补齐这些契约，不能直接以页面能打开作为验收。

## 2. 产品语义与用户体验

### 2.1 智能检索

智能检索只有一个主页面和一个查询范围，但支持两种检索方式：

#### 默认：智能检索

结果按以下顺序展示：

1. AI 综合回答，正文用 `[1]`、`[2]` 等编号标注引用；
2. 来源卡片，包含合集、素材标题、命中片段、内容类型和定位信息；
3. 点击回答中的引用编号，滚动并高亮对应来源卡片；
4. 点击来源，跳到笔记、转写片段或媒体时间点；
5. 来源支持“展开上下文”和“一键收藏”。

相关度分数默认不直接展示给普通用户，必要时放入详情或调试信息。

#### 可选：精确查找

- 对标题、转写、总结、笔记正文和标签做本地关键词检索；
- 只返回命中原文和定位，不生成 AI 综合回答；
- 用于查人名、术语、型号、数字和原句；
- 与智能检索共用范围、类型、标签、时间等筛选条件。

### 2.2 内容库管理

内容库负责组织素材，不承担问答功能：

- 合集、文件夹和标签；
- 同源副本关系；
- 用户笔记正文的修改历史；
- 批量整理和范围筛选；
- 为智能检索提供结构化过滤条件。

### 2.3 收藏夹

收藏夹保留为快速访问入口。第一阶段先完成：

- 智能检索来源一键收藏；
- 收藏状态即时回显；
- 点击收藏项回到对应内容。

收藏分组、收藏内搜索、导入导出在有实际使用量后再增强，不列入首期阻断项。

## 3. 目标架构

```text
┌──────────────────────────────────────────────────────────────┐
│ 智能检索                                                     │
│ 查询 + 范围/类型/标签筛选                                    │
│                                                              │
│ 默认智能检索：AI 综合回答 [1][2] + 可跳转来源卡片             │
│ 精确查找：关键词命中原文 + 定位，不生成 AI 回答                │
└──────────────────────────┬───────────────────────────────────┘
                           │
             ┌─────────────┴─────────────┐
             │ 统一查询契约 / 检索编排层  │
             └─────────────┬─────────────┘
                           │
              ┌────────────┴────────────┐
              │                         │
       向量索引 / reranker         SQLite FTS5 分块索引
       语义召回与 AI 回答           精确召回与原文定位
              │                         │
              └────────────┬────────────┘
                           │
     ┌─────────────────────┴─────────────────────┐
     │ 内容库：合集 / 独立副本 / 同源谱系 / 标签 / 正文版本 │
     └─────────────────────┬─────────────────────┘
                           │
                  收藏夹接收检索结果
```

关键原则：

- 页面只有一个查询入口，检索方式由用户选择；
- AI 回答必须能追溯到来源，来源必须能回到内容；
- 向量索引和 FTS5 都是可重建的检索基础设施；
- 业务元数据只能有一个权威来源；
- 副本独立修改与同源版本可见必须同时成立。

## 5. 统一查询契约

建议先统一响应契约，再决定是否物理合并现有两个后端 service：

```text
request:
  query
  mode: smart | exact
  workspace_ids?
  content_types?
  tag_ids?
  time_range?
  top_k?

response:
  mode
  answer?                 # exact 模式为空
  sources[]
    source_id
    workspace_id
    content_id
    item_type
    item_title
    excerpt
    context_before?
    context_after?
    field
    segment_id?
    start_ms?
    score?
    jump_url
    favorite
  index_status?
```

迁移策略：

1. 先为 `/knowledge/ask` 和 `/search` 补现状契约测试；
2. 新增统一编排层，初期可适配现有两个实现；
3. 前端切到统一响应；
4. `/knowledge` 页面改为跳转，`/knowledge/status`、`/knowledge/rebuild` 暂时保留；
5. 稳定后再判断是否删除重复后端路径。

这种顺序把页面合并与引擎重写解耦，降低一次性改动风险。

## 6. 数据身份与 SQLite 草案

### 6.1 独立副本与同源谱系

产品决定是“复制后可以独立修改，同时能看到其他合集中的同源版本”。因此不能继续把 `item_id` 同时当成“同一内容身份”和“合集内副本身份”。

建议概念模型：

```text
lineage_id：共同来源谱系

lineage L1
├── content A（合集 A，独立内容与正文版本）
├── content B（合集 B，独立内容与正文版本）
└── content C（合集 C，独立内容与正文版本）
```

草案：

```sql
schema_meta(version, migrated_at)

contents(
  content_id PRIMARY KEY,
  lineage_id NOT NULL,
  origin_content_id,
  legacy_item_id,
  content_type,
  created_at,
  updated_at
)

collection_items(
  workspace_id,
  content_id,
  folder_id,
  created_at,
  PRIMARY KEY(workspace_id, content_id)
)

note_versions(
  version_id PRIMARY KEY,
  content_id NOT NULL,
  version_no NOT NULL,
  body_md NOT NULL,
  created_at,
  UNIQUE(content_id, version_no)
)
```

迁移旧数据时：

- 每个 `(workspace_id, item_id)` 生成独立 `content_id`；
- 旧 `item_id` 相同的记录归入同一 `lineage_id`；
- 后续复制创建新的 `content_id`，沿用来源的 `lineage_id`；
- 只提供查看和手动采用其他副本内容，首期不自动覆盖或自动合并。

### 6.2 标签、文件夹与收藏

身份模型稳定后再增加：

```sql
tags(
  tag_id PRIMARY KEY,
  name,
  dimension,
  color,
  parent_id,
  created_at,
  UNIQUE(dimension, name)
)

content_tags(
  content_id,
  tag_id,
  source,                 -- AUTO | MANUAL
  created_at,
  PRIMARY KEY(content_id, tag_id, source)
)

folders(
  folder_id PRIMARY KEY,
  workspace_id,
  parent_id,
  name,
  sort_order,
  created_at
)

favorite_groups(
  group_id PRIMARY KEY,
  name,
  sort_order,
  created_at
)

favorite_items(
  group_id,
  workspace_id,
  content_id,
  note,
  created_at,
  PRIMARY KEY(group_id, workspace_id, content_id)
)
```

原草案中仅以 `item_id` 关联 `item_tags` 和 `content_versions` 会在跨合集副本出现后串数据，必须废弃。

### 6.3 FTS5 分块索引

FTS 索引不能只按素材保存一大行，否则难以返回准确原文和时间位置。建议按内容块索引：

```sql
CREATE VIRTUAL TABLE content_fts USING fts5(
  content_id UNINDEXED,
  workspace_id UNINDEXED,
  field UNINDEXED,        -- title | transcript | summary | note | tags
  segment_id UNINDEXED,
  start_ms UNINDEXED,
  text,
  tokenize='待中文检索验证后确定'
);
```

已验证当前 Python SQLite 支持 FTS5，但中文不能直接使用默认 `unicode61`：

- 默认分词无法命中“发布会”“产品特性”等中文子串；
- `trigram` 可命中三个字以上片段，但无法覆盖“产品”等两个字查询；
- 执行计划必须选择中文分词/多粒度 n-gram 方案，并用真实中文、英文、数字、型号和时间码样例验收。

### 6.4 JSON 与 SQLite 的事实来源

分两阶段处理：

1. **FTS 阶段**：JSON 继续作为内容事实来源，SQLite FTS 只是派生索引；索引可删除并从 JSON 重建。
2. **元数据阶段**：身份、标签、文件夹、收藏和正文版本迁入 SQLite 后，以 SQLite 为这些字段的唯一事实来源；JSON 若需兼容，只输出派生快照，不再双向写入。

必须提供：

- schema version；
- 幂等迁移；
- 迁移前备份；
- 校验统计和失败回滚；
- 索引重建/修复入口；
- 删除、垃圾桶恢复、内容更新和任务完成后的索引同步规则。

## 7. 分期建议

### Phase 0：契约与数据基线

- 固化已确认的产品语义；
- 补 `/knowledge/ask`、`/search`、收藏 API 和关键页面测试；
- 记录查询延迟、索引构建时间、内容规模和失败行为；
- 明确统一响应契约及旧路由兼容期。

### Phase A：统一智能检索页面

- `/search` 改为“智能检索”主入口；
- 默认展示 AI 回答和可定位来源；
- 回答引用定位来源卡片；
- 来源展开上下文、跳转和一键收藏；
- 保留索引状态、覆盖率和刷新入口；
- `/knowledge` 兼容跳转；
- 不改数据存储。

### Phase B：精确查找与可重建 FTS

- 引入 schema version 和 FTS5 分块索引；
- 完成中文检索策略验证；
- 接入标题、转写、总结、笔记正文和标签；
- 支持删除、恢复、编辑后的增量更新及全量重建；
- 上线“不生成 AI 回答”的精确查找模式。

### Phase C：内容身份和权威元数据

- 为现有 `(workspace_id, item_id)` 建立独立 `content_id`；
- 建立 `lineage_id`，迁移当前跨合集重复素材；
- 新复制行为生成独立副本并保留同源关系；
- 再迁移标签、文件夹、收藏分组等元数据；
- 完成备份、幂等迁移、校验和回滚。

### Phase D：正文版本与同源版本查看

- 保存用户笔记正文修改历史；
- 支持查看和恢复当前副本的正文版本；
- 支持查看其他合集中的同源副本；
- 可手动采用其他副本的内容，但不自动覆盖或自动合并。

### Phase E：增强项

- 混合检索和排序调优；
- 收藏内搜索与收藏分组；
- 批量标签/文件夹整理；
- 搜索建议、导入导出等按真实使用反馈决定。

## 8. 风险与验收边界

### 8.1 主要风险

- 当前 `item_id` 可跨合集复用，旧草案主键不足；
- 页面合并若直接重写引擎，可能丢失知识库索引状态和缓存能力；
- 默认 FTS5 分词不能满足中文精确查找；
- JSON 与 SQLite 双权威会产生无法自动解决的一致性问题；
- 数据迁移涉及用户内容，必须可备份、校验和回滚；
- 现有后端基础测试尚未覆盖前端页面与跨模块闭环，重构仍可能出现无声回归。

### 8.2 最低验收

1. 智能检索回答中的每个引用都能定位唯一来源；
2. 来源可展开上下文，并跳到正确笔记、片段或媒体时间点；
3. 来源可一键收藏，收藏夹可立即看到并返回原内容；
4. 精确查找不调用 AI，能命中约定的中文、英文、数字和型号样例；
5. 合集范围、内容类型、标签和时间筛选不串数据；
6. 知识库索引状态、覆盖率、刷新和错误提示在页面合并后仍可用；
7. 复制素材生成独立副本，一个副本修改不影响其他副本；
8. 同源副本可以互相查看，但不会自动覆盖或自动合并；
9. 用户笔记正文可查看和恢复历史版本，AI 总结版本不重复迁移；
10. FTS 索引可从权威内容重建，删除和恢复后不会出现幽灵结果；
11. 数据迁移重复执行不会重复生成记录，失败可回滚；
12. `/knowledge` 等旧入口在兼容期内不会变成死链。
