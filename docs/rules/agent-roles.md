# Codex / Claude Code + 千问协作与接力

> 默认方式：Codex 调查、实测和计划；Claude Code 中的千问执行；Codex 独立审查。Claude 桌面版不再是 NoteBi 的默认计划入口。

## 1. 角色边界

| 工具 | 默认职责 | 默认不做 |
|---|---|---|
| Codex | 调查、运行证据、根因分析、产品/技术计划、编写执行提示词、独立验收 | 千问尚未失败两次前，不默认抢做具体业务实现；计划/调查阶段不启动外部执行器或 Open Design；不主动 push |
| Claude Code + 千问 | 在用户授权执行后，按计划改代码、先红后绿、跑相关测试、commit、输出真实结果 | 不重新规划产品、不扩大范围、不猜接口、不并行开 subagent、不得在计划/调查阶段被启动、缺设计产物时不猜 UI |
| Open Design | 在用户授权执行的 UI 批次中，Codex 调用其产出或审查该批页面/布局/视觉稿/交互方案 | 不写生产代码；计划/调查阶段不调用；没有 UI/设计需求时不强制调用 |
| Claude 桌面版 | 用户明确点名时才用于额外讨论或方案比较 | 不作为本项目默认计划或执行入口 |

当前 Claude Code 通过 CC Switch 路由到千问。终端可能显示 `opus` 等 Claude 别名，不能据此判断实际模型；每次新会话先安全读取模型映射或从新消息元数据确认，禁止输出 token。

## 2. 计划 / 调查与执行隔离（强制）

1. 用户说“先计划”“先调查”或尚未明确同意执行时，Codex 只用本地代码、文档、运行证据和必要的定向测试完成调查与计划。
2. 该阶段**禁止**启动 Claude Code + 千问、调用 Open Design、重启外部工具，或为计划生成完整设计稿；不要把外部工具的排队、重试或故障计入计划时间。
3. 计划交付必须先写清：证据、待用户确认的产品选择、执行批次、验收标准，以及可复制的千问执行提示词。
4. 用户明确说“执行 / 按计划做”后，才启动对应的千问任务；只有该已授权批次涉及 UI 时，才让 Open Design 服务于该批、该页面的设计或视觉审查。
5. 例外：用户在当前轮明确指定要把某个外部工具用于计划本身时，按其明确范围调用，仍须控制为最小范围。

## 3. 默认执行接力链

1. Codex 调查当前 Git、代码和运行状态，形成可验证计划；产品选择交用户确认。
2. Codex 在用户可见终端启动 Claude Code + 千问，传入单一、明确、带红线的执行任务。
3. 千问先补失败测试，再最小实现、跑定向验证、提交一个主题明确的 commit。
4. Codex 不采信执行汇报，独立检查 `git show`、diff、测试和必要运行证据。
5. 首次审查不通过：Codex 把具体 file/line、失败命令和验收差距退回千问修复。
6. **同一根因或同一验收项第二次仍不通过：Codex 直接接管修复，不再第三次退回千问。**

不同问题分别计数；不能把第二个独立问题算成第一个问题的失败次数。

**UI/设计任务分支（仅限已授权执行批次）**：

1. 涉及用户可见 UI 页面、布局、视觉稿、交互流程或视觉审查时，Codex 可先用 Open Design 产出或审查设计方案。
2. Codex 把已确认的设计产物、约束和验收点交给千问；千问只负责实现，不做设计。
3. 千问缺少设计产物、或设计与代码事实矛盾时，必须停止回报，不得自行猜 UI。
4. 实现完成后，Codex 仍独立审查最终 UI 和运行证据；设计评审通过不免除实现审查。
5. 没有 UI/设计需求时不调用 Open Design。

## 4. 可见终端与会话清理

- 优先使用 Codex 右侧/集成终端，让用户实时看到 Claude Code 的读取、测试、修改和提交。
- 当前产品无法直接写入右侧终端时，打开前台可见的 macOS Terminal 窗口；不要静默跑长后台会话。
- 同一问题的连续返修可以 resume 原会话，以保留证据和失败上下文。
- Open Design 同样适用：同一设计返修可以保留上下文；新的、无关的设计任务必须先清理旧上下文并重新对账 Git 与设计产物。
- **不同问题、互不依赖的批次、以及每次新建 Claude Code 任务前，必须 `/clear` 或退出后启动全新会话。**
- 清理前记录必要的 commit / 测试结果；清理后先跑 Git 对账，不重新全量读旧上下文。
- 启动新会话前确认旧进程已停止；同一工作区任何时候只允许一个代码执行者。
- Codex 至少在“任务开始、红灯确认、绿灯确认、commit 完成”四个节点向用户同步。

## 5. 给千问的执行提示词模板

```text
你是 Claude Code 中的千问执行者，只执行下面已经确认的任务。
不要重新规划，不要全项目调查，不要开 subagent，不要安装依赖，不要 push。

启动先跑：
git status --short --branch
git log --oneline -5

若分支、HEAD 或工作区不符，立即停止报告。
只读任务直接相关文件；大文件先 rg 定位再读片段。
严格 TDD：先写最窄失败测试并实际看到失败，再做最小实现，最后跑相关回归。
实际接口、数据结构、依赖或产品行为与任务不一致时停止，不得自行扩大。
完成后提交一个 commit，并输出：真实改动文件、红灯命令/原因、绿灯命令/数字、commit hash、未验证项。

任务：
<目标、涉及文件/接口、验收标准、禁止事项>
```

## 6. Codex 审查与返修模板

```text
结论：通过 / 不通过 / 需要补充验证

独立证据：
- git show / diff 范围
- Codex 实际跑过的命令、数量和退出码

问题：
- <file:line + 用户可见影响 + 为什么现有测试没覆盖>

返修提示词（首次失败才给千问）：
- 只修上述同一问题
- 先补能复现的失败测试
- 不 amend、不 push、不扩大范围
```

第二次仍失败时，Codex 在原范围内直接实现并复验；涉及 schema、权限、安全、依赖、数据迁移或新的产品取舍仍必须先问用户。

## 7. 禁止默认全项目模式

除非用户明确要求“全项目体检 / 全量梳理 / 通读全部代码 / 并行调研”，任何工具不得启动全库扫描或并行 agent。即使命中，也先说明范围和预算；本项目默认串行执行。

## 8. 干净验证纪律

1. 核对单个 commit 必须在干净环境；其它未提交改动不能替目标 commit 兜底。
2. 报告文件必须与 `git show --stat <hash>` 一致，不凭记忆写。
3. 测试命令必须记录真实退出码；管道、超时和 flaky 首轮失败要如实报告。
4. Codex 审查时优先复跑最窄相关测试，再按风险决定 build、全量或浏览器验证。
5. 不 push；是否合并由用户决定。
