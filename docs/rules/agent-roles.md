# NoteBi Codex 直接执行与工具协作

> 默认方式：Codex 调查、实测、计划、实现、测试、提交和验证。Claude Code / 千问不是默认执行步骤；只有用户在当前任务明确要求时才可调用。

## 1. 角色边界

| 工具 | 默认职责 | 默认不做 |
|---|---|---|
| Codex | 调查、运行证据、根因分析、产品/技术计划、实现、TDD、测试、提交、独立验证 | 未获执行授权时写业务功能；主动 push；凭猜测改变产品语义 |
| Claude Code / 千问 | 用户当前任务明确指定时，可承担限定的实现或复验工作 | 不作为默认执行器；不重新规划产品；不扩大范围；不替代 Codex 的最终验证 |
| Open Design | 已授权 UI 批次的页面、布局、视觉与交互设计/评审 | 不写生产代码；计划/调查阶段不调用；没有 UI 需要时不强制调用 |
| Claude 桌面版 | 用户明确点名时用于额外讨论或方案比较 | 不作为本项目默认计划或执行入口 |

## 2. 计划 / 调查与执行隔离（强制）

1. 用户说“先计划”“先调查”或尚未明确同意执行时，Codex 只用本地代码、文档、运行证据和必要的定向测试完成调查与计划。
2. 该阶段不启动外部执行器、Open Design 或完整设计稿生成；不要把外部工具的排队、重试或故障计入计划时间。
3. 计划交付必须写清：证据、待用户确认的产品选择、执行批次和验收标准。
4. 用户明确说“执行 / 按计划做”后，Codex 在已确认范围内直接实现。
5. 只有用户在当前任务明确要求 Claude Code / 千问时，才可将一个边界清楚的子任务交给它；外部结果必须由 Codex 复验。
6. 只有已授权批次涉及 UI 时，才让 Open Design 服务于该批、该页面的设计或视觉审查。

## 3. 默认执行链

1. Codex 对账当前 Git、代码和运行状态，形成可验证计划；产品选择交用户确认。
2. 获得执行授权后，Codex 先写能复现问题的最窄失败测试，再做最小实现。
3. Codex 运行定向测试、必要回归、`git diff --check`，并对 UI 运行适当的浏览器验证。
4. 每个完成批次形成一个主题明确的本地 commit，不 push。
5. Codex 复核自己的 diff、测试退出码和运行证据；事实与计划不一致时按停点规则报告用户。

## 4. UI / 设计任务分支

1. 涉及用户可见 UI 页面、布局、视觉稿、交互流程或视觉审查时，Codex 可先用 Open Design 产出或审查设计方案。
2. Codex 以确认的设计产物、当前代码与数据契约共同实现，不凭文字臆造新版布局。
3. 设计产物与真实组件或数据契约冲突时，停止并向用户报告；不得修改产品语义来迁就设计稿。
4. 实现完成后，Codex 仍须独立验证最终 UI 和运行证据；设计评审通过不免除实现验证。

## 5. 外部工具与会话

- Claude Code 仅在用户明确要求时启动；启动前后都要对账 Git，且同一工作区严格串行。
- 用户没有要求 Claude Code 时，不把实现、测试或 commit 默认交出去。
- Open Design 的同一设计返修可以保留上下文；新的、无关设计任务先清理旧上下文并重新对账 Git 与设计产物。
- Codex 至少在“任务开始、红灯确认、绿灯确认、commit 完成”四个节点向用户同步。
